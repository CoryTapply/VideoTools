## Spike A — real remux with streamed output

The biggest unresolved unknown in the project, and it folds in the export-write test that M0 never ran.

```
Context: I'm building a browser-based video trimmer for 20GB+ local files. Earlier
spikes confirmed that File.slice() streams lazily, that I can walk to a moov at the
end of a 27GB file and parse it in ~19ms, and that <video> seek costs ~220ms. What
is completely untested is the thing the product actually does: producing a real,
playable trimmed MP4 by rewriting sample tables, streamed to disk.

Build this in the existing harness at src/spikes/A-remux/.

GOAL: given the 27GB OBS fixture and an in/out time range, produce a playable MP4
containing only that range, written directly to disk, with flat memory.

STEP 1 — full sample index for all tracks.
Extend the existing spike2 parser. For each track in moov, expand the stbl into
per-sample data:
  - stts (time-to-sample, run-length encoded) -> per-sample duration and DTS
  - ctts if present -> composition offsets. Handle BOTH version 0 (unsigned) and
    version 1 (signed) offsets; getting this wrong silently breaks B-frame ordering
  - stsz, or stz2 if that's what the file uses -> per-sample size
  - stsc + stco/co64 -> per-sample absolute byte offset. This requires walking the
    sample-to-chunk table and accumulating sizes within each chunk. This is the
    fiddly part; write it carefully and test it in isolation
  - stss -> sync sample numbers. NOTE: these are 1-BASED sample numbers, a classic
    off-by-one. If stss is absent, every sample is a sync sample
Store as preallocated typed arrays (Float64Array for pts/dts/offset, Uint32Array
for size, Uint8Array for sync flags). Report build time and retained bytes.

Also read and report: mvhd timescale and duration, each tkhd's track id, duration
and display matrix, each mdhd's media timescale and duration, and whether any track
has an edts/elst edit list. If an edit list exists, print it and stop — I need to
decide how to handle it deliberately rather than silently dropping it.

STEP 2 — sample selection.
Given in/out times in seconds:
  - video in-sample = the last sync sample whose composition time <= in
  - video out-sample = the last sample whose composition time <= out
  - audio: select samples whose time range overlaps [in-sample's time, out-sample's
    time], using the AUDIO track's own timescale, not the video one
Report the actual in-time of the chosen keyframe and how far it shifted from the
request. On this fixture expect a shift of up to ~4.2 seconds.

STEP 3 — two-pass write, faststart output.
Do NOT buffer the output. Do NOT build the file in memory. Structure it as:
  Pass 1 (metadata only, no media bytes read): compute all rewritten tables and
  therefore the exact byte size of the new moov.
  Pass 2: showSaveFilePicker() -> createWritable() -> write moov first (now that
  its size is known, so mdat offsets are computable), then stream mdat by reading
  sample ranges from the source File and piping them straight out.
This gives a faststart file in a single copying pass.

Tables to rewrite:
  - stts: recompute run-length encoding over the selected samples' durations
  - ctts: same, preserving version and signedness
  - stss: reindex sync samples to the new 1-based numbering
  - stsz: selected sizes
  - stsc / stco or co64: choose a chunk layout. Interleave audio and video in
    roughly 1-second groups so the output is seekable and streamable — do not write
    all video then all audio
  - stsd: copy verbatim, byte for byte. Do not attempt to regenerate it
  - tkhd, mdhd, mvhd durations: update to the new duration in the right timescale
Rebase timestamps by subtracting the first selected sample's DTS per track.

CRITICAL: if the output mdat exceeds 4.29GB you must write the 64-bit largesize
form (size field = 1, followed by a 64-bit size). This is the write-side twin of
the read-side bug already fixed in spike2. Test it deliberately by exporting a
range large enough to trip it.

STEP 4 — validation. This matters more than the performance numbers.
  - open the output in Chrome, and print instructions to check VLC and QuickTime
  - run ffprobe -count_frames on the output and compare frame count, duration, and
    stream parameters against expectation
  - produce a reference with `ffmpeg -ss X -to Y -i input -c copy ref.mp4` and
    compare frame counts, durations, and per-track timescales against yours.
    They will not be byte-identical; I care that they agree structurally
  - verify A/V sync by checking the first and last audio sample times against the
    first and last video sample times
  - export three ranges: one near the start, one mid-file, one ending at the very
    last frame. The last one exercises truncation edge cases

STEP 5 — measurements.
  - index build time and retained bytes (step 1)
  - table rewrite time (pass 1)
  - export throughput in MB/s (pass 2)
  - JS heap sampled every 250ms across the whole export
  - source read chunk size sweep: 256KB, 1MB, 4MB, 16MB — report throughput each
  - abort mid-export via AbortSignal and report what's left on disk: truncated,
    empty, locked, or a file that opens and plays but is incomplete

FAIL CONDITIONS, report each explicitly:
  - output doesn't play in all three players
  - frame count or duration disagrees with the ffmpeg reference
  - heap growth during export above ~100MB
  - export throughput below ~100MB/s
  - A/V drift detectable at the end of a 5-minute export
  - aborted export leaving a file that plays but is silently incomplete

Keep this focused on MP4/MOV with H.264 + AAC. Do not generalise to other
containers or codecs. Do not build an abstraction layer — this is a spike.
```

## Spike B — sample index at scale

M0's spike 2 parsed the `stss` table (1,015 keyframes) in 18.6ms. The real index is ~253,000 samples and was never built. Spike A produces it as a side effect; this spike stress-tests it.

```
Context: spike A built a full per-sample index from an MP4's stbl. This spike
characterises it at scale and validates it against a reference implementation,
because every downstream subsystem (frame stepping, thumbnails, trim point
resolution) depends on it being correct and cheap.

Build at src/spikes/B-index/, reusing spike A's index builder.

1. CORRECTNESS FIRST. Cross-check against mediabunny on the same file:
   - compare total sample count per track
   - compare 1,000 randomly chosen samples on pts, dts, byte offset, size, and sync
     flag
   - compare the full keyframe timestamp list
   Print every mismatch with the sample index and both values. Do not summarise as
   a pass/fail percentage — I want to see the actual disagreements. Repeat against
   vfr-screen.mp4, where variable frame durations are most likely to expose a bug
   in the stts run-length expansion.

2. SCALE. Run against the 27GB OBS file (~253k samples) and report:
   - index build time, broken down by stage: stts expansion, ctts, stsz,
     stsc+stco offset computation
   - peak heap during build vs retained heap after
   - exact retained byte size of the typed arrays
   - bytes actually read from disk during the build (instrument and sum your reads)
   Then extrapolate: what would an 8-hour recording at 60fps (~1.7M samples) cost?
   If the answer is bad, say so plainly and tell me whether the cost is dominated
   by the stsc offset walk or by raw parse.

3. QUERIES. Time these against the typed arrays, 10,000 iterations each, report
   ns/op:
   - frame index at an arbitrary timestamp (binary search)
   - nearest preceding sync sample to an arbitrary timestamp
   - exact PTS of frame N, N+1, N-1 (the frame-stepping path)
   - the byte range for a given sample
   These need to be fast enough to run inside a pointermove handler.

4. WORKER TRANSFER. postMessage the index to a Worker as transferables. Time it and
   confirm zero-copy by checking the source arrays have byteLength 0 afterwards.
   Then measure the same transfer via a SharedArrayBuffer-backed copy for
   comparison, since I may want multiple workers reading it simultaneously.

5. VFR. For vfr-screen.mp4, explicitly report whether sample durations are
   constant, the min/max/median duration, and the implied nominal frame rate. I
   need hard confirmation that I cannot assume a fixed frame rate anywhere.

6. PERSISTENCE. Serialise the index to OPFS as raw typed-array bytes, then read it
   back. Time both. Compare against the cost of rebuilding from the file. This
   determines whether index caching is worth building in M1.

FAIL CONDITIONS:
  - any mismatch against mediabunny
  - build time on the 27GB file above ~5s
  - retained index above ~150MB
  - extrapolated 1.7M-sample index above ~400MB retained
  - any query above ~1 microsecond
```

## Spike C — WebCodecs, for scrubbing not just thumbnails

M0 measured `<video>` seek at 220ms, which rules out drag-to-scrub. This spike tests whether WebCodecs can carry both the filmstrip and the scrub interaction.

```
Context: <video> seek on my target file averages 220ms, far too slow for
drag-to-scrub at 60fps. I want to know whether a WebCodecs-backed frame cache can
serve the scrub interaction instead, and how fast the filmstrip fills. Note the
real-world GOP on this footage is ~4.2 seconds (~250 frames at 60fps), which makes
random access via WebCodecs non-obvious — reaching an arbitrary frame may require
decoding a long dependency chain.

Build at src/spikes/C-decode/, using the index from spike A/B.

1. KEYFRAME THROUGHPUT (the filmstrip path). In a Worker:
   - take 200 keyframes spread across the 27GB file
   - file.slice(offset, offset+size) -> arrayBuffer() -> EncodedVideoChunk with
     type 'key' -> VideoDecoder
   - on output: createImageBitmap(frame, {resizeWidth:160, resizeHeight:90}) then
     frame.close() IMMEDIATELY
   - report thumbnails/second, with time split across disk read, decode, downscale
   - compare hardwareAcceleration 'prefer-hardware' vs 'prefer-software'
   - rerun with reads coalesced into 4MB windows and report the difference

2. ARBITRARY-FRAME LATENCY (the scrub-settle path). THIS IS THE KEY MEASUREMENT.
   For 50 random non-keyframe targets:
   - find the preceding sync sample, decode forward through the GOP discarding
     output until the target frame, then render it
   - report the full distribution: p50, p95, p99, max, and the mean number of
     frames decoded per request
   - compare directly against the 220ms <video> seek baseline on the same targets
   With a 4.2s GOP this could be worse than <video>, not better. If it is, say so
   clearly — that's a real finding and it changes the scrub design.
   Then test whether keeping a warm decoder and decoding forward from the CURRENT
   position (rather than restarting from a keyframe) makes sequential forward
   scrubbing cheap, which is the common case during a drag.

3. CACHE-BACKED SCRUB SIMULATION. Pre-generate a decoded frame cache at 2fps
   across a 5-minute window (600 frames at 320x180). Then simulate a drag: request
   frames along a swept timeline position at 60Hz for 5 seconds.
   - report cache hit latency, hit rate, and whether 60Hz is sustainable
   - report the memory held by 600 cached ImageBitmaps, then close them all and
     confirm heap returns to baseline
   This is the interaction I want to ship. Tell me whether it works.

4. LEAK TEST, run in isolation: decode 100 keyframes WITHOUT calling frame.close().
   Report how many complete before the decoder stalls, and the exact error. I want
   to see the failure mode so I recognise it in production.

5. ATLAS. Pack 100 thumbnails into a 10x10 WebP sprite at quality 60. Report atlas
   bytes and encode time, write to OPFS, and time the read-back and decode of a
   single thumbnail from the atlas.

6. Run keyframe throughput against both the 27GB file and longgop.mp4, and report
   the actual keyframe interval measured for each.

FAIL CONDITIONS:
  - keyframe decode below ~50 thumbnails/second
  - cache-backed scrub unable to sustain 60Hz
  - heap not returning to baseline after closing bitmaps
  - arbitrary-frame latency worse than the <video> baseline AND warm-decoder
    forward scrubbing also failing to help — that combination means the scrub
    design needs rethinking entirely
```

## Synthesis

```
Read every JSON result in results/ from both the M0 and M0.5 runs and update
results/M0-FINDINGS.md into results/FEASIBILITY.md.

Structure:

1. Headline table: index build time and retained size, remux export throughput,
   export heap delta, keyframe decode rate, arbitrary-frame latency vs <video>
   baseline, cache-backed scrub sustainable Hz.

2. Per-spike verdict against the stated fail conditions: go / go-with-changes /
   no-go. Say which, plainly.

3. "Design changes required" — every place a measurement contradicts the
   architecture document. Be blunt. Specifically address:
   - is drag-to-scrub via a frame cache viable, or does the interaction change
   - does the index need to be chunked or lazily built for very long files
   - what the real-world GOP length means for the keyframe-shift UI
   - whether faststart output is affordable in one pass

4. "Constants for M1" — concrete numbers to build against: read chunk size,
   thumbnail worker concurrency, index cache strategy, expected export MB/s for
   progress estimation, scrub cache window size and frame rate.

5. "Known gaps" — what remains untested, and whether each is a launch blocker or
   can be deferred. Include the fact that all measurements come from one M1 Max
   with fast NVMe, and note which numbers would degrade most on slower storage.

Do not soften unfavourable results.
```
